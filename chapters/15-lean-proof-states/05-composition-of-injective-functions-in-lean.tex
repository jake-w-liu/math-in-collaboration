\section{Composition of injective functions in Lean}\label{ch15:sec:injcomp}
Our next example is Theorem~\ref{thm:injcomp}: if $f:A\to B$ and $g:B\to C$ are injective, then so is $g\circ f$. Stating it needs a little more notation for functions.

\subsection*{Arrows and implicit parameters}
If \code{A} and \code{B} are types, then \code{A -> B} is the type of functions from \code{A} to \code{B}, and \code{f : A -> B} is the Lean form of $f:A\to B$. Do not confuse this arrow, which builds a type, with the \code{=>} in \code{fun x => x + 1}, which separates the input of one particular function from its rule.

A function of two inputs has two arrows in its type: \code{A -> B -> C} means \code{A -> (B -> C)}, so such a function takes an input of type \code{A} and returns a function from \code{B} to \code{C}. For example, Lean's addition \code{Nat.add} has type \code{Nat -> Nat -> Nat}; \code{Nat.add 2} is the function $n\mapsto 2+n$, and \code{Nat.add 2 3} is $5$. This is why several inputs are written one after another, and why \code{f x y} means \code{(f x) y}.

The sets $A$, $B$, $C$ of a mathematical statement become types: just as \code{P : Prop} says that $P$ is a proposition, \code{A : Type} says that \code{A} is a type of ordinary mathematical objects, such as \code{Nat}. Below, such parameters are written in curly braces, as in \code{\{A B : Type\}}. Braces mark \emph{implicit} parameters, which Lean works out from the other inputs: when we write \code{Inj f}, Lean already knows that \code{f : A -> B}, so we need not write \code{A} and \code{B}. Parameters in round brackets are \emph{explicit} and must be written at every use. Implicit parameters are still part of the statement, just not written out each time.

\subsection*{The definition and the theorem}
We write the definition of injectivity from Section~\ref{ch03:sec:injsurj} ourselves, so that every part of it is visible.
\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
def Inj {A B : Type} (f : A -> B) : Prop :=
  forall x y : A, f x = f y -> x = y

theorem inj_comp {A B C : Type}
    (f : A -> B) (g : B -> C)
    (hf : Inj f) (hg : Inj g) :
    Inj (fun x => g (f x)) := by
  intro x y h
  have hxy : f x = f y := hg (f x) (f y) h
  exact hf x y hxy
\end{lstlisting}
\end{minipage}\par

The definition makes \code{Inj f} a proposition, as the \code{: Prop} says. The word \code{forall} is Lean's keyboard spelling of $\forall$, which the infoview prints, so \code{forall x y : A} means ``for all $x$ and $y$ in $A$''; the comma ends the list of variables. Lean reads each equation as a unit before the arrow, so \code{f x = f y -> x = y} means \code{(f x = f y) -> (x = y)}. Altogether, \code{Inj f} is the statement $\forall x,y\in A,\ f(x)=f(y)\Rightarrow x=y$ used in Chapter~\ref{ch:maps}.

The theorem has implicit parameters \code{A}, \code{B}, \code{C}, explicit functions \code{f} and \code{g}, and hypotheses \code{hf : Inj f} and \code{hg : Inj g}. Its claim is \code{Inj (fun x => g (f x))}, where \code{fun x => g (f x)}, which sends $x$ to $g(f(x))$, is $g\circ f$ written without a name.

The proof uses one more fact: a proof of a ``for all'' statement is used like a function. It accepts any element and returns a proof of the statement for that element, just as a proof of \code{P -> Q} turns proofs of $P$ into proofs of $Q$. Since Lean can replace \code{Inj g} by its definition, \code{hg} is such a rule. Applied to two elements \code{b1} and \code{b2} of \code{B}, it gives a proof of \code{g b1 = g b2 -> b1 = b2}, and applying that to a proof \code{e} of \code{g b1 = g b2} gives \code{hg b1 b2 e}, a proof of \code{b1 = b2}. So \code{hg} takes three inputs, two elements of \code{B} and evidence that their values under $g$ agree, and returns evidence that the two elements are equal. The same holds for \code{hf}, with elements of \code{A}.

Now the proof, line by line.
\begin{itemize}
\item Replaced by its definition, the goal \code{Inj (fun x => g (f x))} is a ``for all'' statement followed by an implication, so \code{intro} can look inside it. On a ``for all'' statement, \code{intro x} does what ``take any $x$'' does on paper: it adds an arbitrary element \code{x} and removes the quantifier from the goal. On an implication, \code{intro} assumes the hypothesis, as in Section~\ref{ch15:sec:implication}. So \code{intro x y h} introduces arbitrary \code{x} and \code{y} in \code{A} and a hypothesis \code{h} that their outputs under the composition agree, and the goal becomes \code{x = y}. On paper: ``Take any $x,y\in A$ and assume $g(f(x))=g(f(y))$.''
\item In \code{hg (f x) (f y) h}, the two elements of \code{B} are \code{f x} and \code{f y}, not \code{x} and \code{y}, and \code{h} is the evidence that their values under $g$ agree. The result, recorded as \code{hxy}, proves \code{f x = f y}. On paper: ``Injectivity of $g$ gives $f(x)=f(y)$.''
\item Finally, \code{hf x y hxy} proves exactly the goal \code{x = y}. On paper: ``Injectivity of $f$ then gives $x=y$.''
\end{itemize}
The Lean proof takes the same two steps as the proof of Theorem~\ref{thm:injcomp}, in the same order.

When Lean rejects an application, compare the types of its pieces. Skipping the middle step and writing \code{exact hf x y h} gives an ``application type mismatch'' error, because \code{hf} needs evidence that \code{f x = f y}, while \code{h} is evidence about outputs of $g$. The missing step is exactly what injectivity of $g$ supplies.

In the editor, Lean displays the hypothesis \code{h} as
\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
h : (fun x => g (f x)) x = (fun x => g (f x)) y
\end{lstlisting}
\end{minipage}\par
rather than as \code{g (f x) = g (f y)}. The expression \code{(fun x => g (f x)) x} means ``apply the rule $x\mapsto g(f(x))$ to the input $x$,'' which evaluates to \code{g (f x)}. Inside \code{fun x => g (f x)}, the letter \code{x} is only a placeholder, like the $x$ in $x\mapsto g(f(x))$; the \code{x} after the closing parenthesis is the element of \code{A} that \code{intro} introduced. Evaluating an application of a \code{fun} expression by putting the actual input in place of the placeholder is called \emph{beta-reduction}, one more kind of the reduction of Section~\ref{ch15:sec:symbols}. When Lean checks that a proof has the right type, it treats a proposition and its beta-reduced form as the same, which is why \code{hg} accepts \code{h}. Some tactics, however, look for the literal written form of an expression; Section~\ref{ch16:sec:surj} shows a case where we must first restate the goal in its beta-reduced form.
