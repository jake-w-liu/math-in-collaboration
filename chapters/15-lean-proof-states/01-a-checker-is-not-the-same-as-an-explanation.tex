\section{A checker is not the same as an explanation}\label{ch15:sec:checker}
Lean is a programming language and a \emph{proof assistant}: a program that checks proofs. You write a statement and its proof in a precise formal language, and Lean examines every step. If a step does not follow from what came before, Lean reports an error at that step. If Lean accepts the whole proof without any error or warning, then every step has been checked.

Lean is built around one idea. Every expression in Lean has a \emph{type}, which says what kind of object it is. The natural number $3$ has the type of natural numbers, and a function from natural numbers to natural numbers has a function type. Lean treats propositions in the same way: each proposition is itself a type, and a proof of the proposition is an object of that type. For example, the equation $2+2=4$ is a type, and a proof of this equation is an object of that type; the next section shows how such a proof is written. Checking a proof therefore comes down to checking that an object really has the type claimed for it. In practice, proofs are rarely written out as objects directly. They are written with \emph{tactics}, instructions that build the proof object step by step, much as the sentences of a written proof build an argument. The official introductions explain these ideas in more detail~\cite{leanprop,leantactics}.

Checking a proof is not the same as explaining it. When Lean accepts a proof, you know that every step is valid. You do not yet know why the argument works, which step carries the main idea, or whether the statement says what you meant it to say. That understanding is still your job. It matters even more when a formal proof comes from an AI assistant, because a proof that Lean accepts can still be a proof of the wrong statement; Section~\ref{ch16:sec:irrelevant} gives examples. For this reason, every Lean proof in this chapter is placed beside the ordinary argument it encodes.

You will not need to memorize a catalogue of tactics. The aim of this chapter is to make the proof state of Section~\ref{ch04:sec:directions} explicit: at each moment of a proof, which objects and facts are available, and what exactly remains to be shown? The examples prove facts that you already know from Chapters~\ref{ch:logic} and~\ref{ch:maps}. That way, a difficulty with Lean's notation can be told apart from a difficulty with the mathematics.

You can read this chapter without installing anything. To run the examples yourself, install Lean by following the official instructions~\cite{leaninstall}. They set up the free editor VS Code together with its Lean~4 extension. The examples in Chapters~\ref{ch:lean1} and~\ref{ch:lean2} use only the libraries that come with Lean itself, not the large mathematical library Mathlib, and they are written for Lean version~4.19.0.

\subsection*{What a Lean file looks like}
A Lean file is an ordinary text file whose name ends in \code{.lean}, for example \code{proofs.lean}. It contains \emph{declarations}: some define new objects, and others state and prove results. All the examples in Chapters~\ref{ch:lean1} and~\ref{ch:lean2} can go into one file of the following shape; Appendix~\ref{app:practical} gives more detail.
\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
import Std

namespace MathCourse

-- the definitions and theorems go here

end MathCourse
\end{lstlisting}
\end{minipage}\par
The first line, \code{import Std}, makes Lean's standard library available. The line \code{namespace MathCourse} starts a group of names. Every definition and theorem between it and \code{end MathCourse} receives the prefix \code{MathCourse}, so that, for example, the full name of the definition \code{twice} in the next section is \code{MathCourse.twice}. This keeps our names from colliding with names that Lean's libraries already use. The word \code{end} here closes the group of names; it has nothing to do with the end of a proof. Everything from \code{-{}-} to the end of a line is a \emph{comment}, which Lean ignores.

There are two ways to check the file. In the editor, Lean checks the file continuously as you type. When the cursor is inside a proof, a panel beside the file, called the \emph{infoview}, shows the proof state at that point: the facts that are available and what remains to be proved. Alternatively, from a terminal---a window for typing commands to installed programs---the command \code{lean proofs.lean} checks the whole file at once. If it prints nothing, every declaration was accepted, without any error or warning. The proofs themselves are always typed into the file, never into the terminal.

Once Lean is installed, move the cursor through each proof one line at a time and compare the proof state in the infoview with the explanation in the text.
