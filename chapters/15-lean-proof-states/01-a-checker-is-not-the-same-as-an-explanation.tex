\section{A checker is not the same as an explanation}\label{ch15:sec:checker}
Lean is a programming language and a \emph{proof assistant}: a program that checks proofs. You write a statement and its proof in a precise formal language, and Lean reports an error at any step that does not follow from what came before. If Lean accepts the whole proof without any error or warning, every step has been checked.

Lean is built around one idea: every expression has a \emph{type}, which says what kind of object it is. The number $3$ has the type of natural numbers. Propositions are types too, and a proof of a proposition is an object of that type, so checking a proof comes down to checking that an object really has the type claimed for it. Proofs are usually written with \emph{tactics}, instructions that build the proof object step by step, much as the sentences of a written proof build an argument~\cite{leanprop,leantactics}.

Checking a proof is not the same as explaining it. When Lean accepts a proof, you know that every step is valid, but not why the argument works, which step carries the main idea, or whether the statement says what you meant. That understanding is still your job, especially when a formal proof comes from an AI assistant: a proof that Lean accepts can still be a proof of the wrong statement (Section~\ref{ch16:sec:irrelevant}). So every Lean proof in this chapter is placed beside the ordinary argument it encodes.

The aim is not a catalogue of tactics but the proof state of Section~\ref{ch04:sec:directions}, made explicit: at each moment, which objects and facts are available, and what remains to be shown? The examples prove facts you already know from Chapters~\ref{ch:logic} and~\ref{ch:maps}, so that a difficulty with Lean's notation can be told apart from a difficulty with the mathematics.

You can read this chapter without installing anything. To run the examples, install Lean by following the official instructions~\cite{leaninstall}, which set up the free editor VS Code with its Lean~4 extension. The examples in Chapters~\ref{ch:lean1} and~\ref{ch:lean2} are written for Lean~4.19.0 and use only the libraries that come with Lean, not the large mathematical library Mathlib.

\subsection*{What a Lean file looks like}
A Lean file is a text file whose name ends in \code{.lean}, such as \code{proofs.lean}. It contains \emph{declarations}, which define new objects or state and prove results. All the examples in Chapters~\ref{ch:lean1} and~\ref{ch:lean2} can go into one file of this shape:
\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
import Std

namespace MathCourse

-- the definitions and theorems go here

end MathCourse
\end{lstlisting}
\end{minipage}\par
The line \code{import Std} makes Lean's standard library available. Every name declared between \code{namespace MathCourse} and \code{end MathCourse} receives the prefix \code{MathCourse}, which keeps our names from colliding with names in Lean's libraries; this \code{end} has nothing to do with the end of a proof. Everything from \code{-{}-} to the end of a line is a \emph{comment}, which Lean ignores.

In the editor, Lean checks the file as you type. When the cursor is inside a proof, a panel beside the file, called the \emph{infoview}, shows the proof state at that point: the facts that are available and what remains to be proved. Appendix~\ref{app:practical} explains how to set up such a file and how to check all of it at once from a terminal.
